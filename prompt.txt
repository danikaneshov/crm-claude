# CRM для кальянных мастеров

## 1. Общая концепция

Необходимо разработать CRM для кальянного бизнеса.

Система должна состоять из:

1. **Telegram Mini App** — приложение для кальянных мастеров.
2. **Telegram Bot** — точка входа и авторизации мастеров.
3. **Web Admin Panel** — отдельная админ-панель для владельца/администратора.
4. **Backend** — серверная бизнес-логика.
5. **Firebase / Firestore** — основная база данных.
6. **Firebase Storage не использовать для фотографий отчётов**, фотографии хранить в отдельном закрытом Telegram-канале.
7. **Gemini AI** использовать для анализа фотографий отчётов.
8. Исходный код хранить в **GitHub**.
9. Frontend и web-приложения деплоить через **Vercel**.

Архитектура должна изначально поддерживать несколько точек.

Сейчас существует:

```text
Точка 1
Точка 2
```

Но в будущем количество точек может увеличиться:

```text
Точка 3
Точка 4
...
```

Поэтому нельзя жёстко зашивать в код только две точки.

---

# 2. Основная архитектура

Общая схема:

```text
                    Telegram
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
       Telegram Bot        Telegram Mini App
             │                   │
             │             Telegram initData
             │                   │
             └─────────┬─────────┘
                       ▼
                    Backend
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      Firestore     Telegram      Gemini
                     Storage        AI
          │            │            │
          └────────────┴────────────┘
                       │
                       ▼
                 Business Logic
                       │
                       ▼
                  Admin Panel
```

---

# 3. Авторизация мастеров

PIN-коды полностью убрать.

Мастер идентифицируется через Telegram.

Основной идентификатор:

```text
telegram_id
```

Не использовать Telegram username как основной идентификатор.

Username может отсутствовать или измениться.

---

# 4. Создание мастера

Администратор в Admin Panel создаёт сотрудника.

Например:

```text
Имя:
Данияр

Telegram ID:
123456789

Оклад:
3000 ₸

Ставка за продажу:
1500 ₸

Статус:
Активен
```

Можно также предусмотреть возможность сначала создать сотрудника без Telegram ID.

Например:

```text
Имя: Данияр
Telegram ID: не привязан
Статус: Ожидает привязки
```

После того как сотрудник нажмёт `/start` в Telegram-боте, его Telegram ID может быть привязан к существующему сотруднику через предусмотренную бизнес-логику.

Предпочтительно, чтобы администратор контролировал привязку и нельзя было произвольно привязать Telegram аккаунт к чужому сотруднику.

---

# 5. Telegram Bot

Бот является входной точкой для мастера.

Мастер:

```text
Открывает бота
      ↓
Нажимает /start
      ↓
Backend получает Telegram ID
      ↓
Ищет сотрудника в Firestore
      ↓
Проверяет активность
      ↓
Отправляет кнопку «Открыть CRM»
```

Если сотрудник отсутствует:

```text
Доступ к CRM не предоставлен.

Обратитесь к администратору.
```

Если сотрудник найден:

```text
[ Открыть CRM ]
```

Кнопка открывает Telegram Mini App.

---

# 6. Защита Mini App

Критически важно не доверять Telegram ID, переданному обычным frontend-параметром.

Mini App должен передавать на backend официальный Telegram `initData`.

Backend обязан самостоятельно валидировать Telegram `initData`.

После успешной проверки backend получает подтверждённый Telegram ID.

После этого:

```text
validatedTelegramId
        ↓
Firestore employees
        ↓
telegram_id == validatedTelegramId
        ↓
is_active == true
        ↓
ACCESS GRANTED
```

Если сотрудник не найден:

```text
ACCESS DENIED
```

Даже если пользователь:

* знает URL Mini App;
* открыл Mini App напрямую;
* изменил данные frontend;
* отправил чужой employee ID;
* попытался подменить Telegram ID.

Доступ всегда должен определяться backend.

---

# 7. Firebase

Использовать:

```text
Firebase Firestore
Firebase Authentication
```

Firebase Authentication использовать для авторизации Admin Panel.

Мастера не должны вводить логины/пароли/PIN.

Для мастеров используется Telegram authentication flow через Mini App.

Также можно использовать Firebase Storage для других файлов в будущем, но **фотографии отчётов r_keeper туда не загружать**.

---

# 8. Telegram как файловое хранилище

Фотографии отчётов необходимо хранить в отдельном закрытом Telegram-канале.

Например:

```text
CRM Reports Storage
```

Канал должен быть закрытым.

Telegram-бот является администратором канала.

Когда мастер загружает фотографию отчёта:

```text
Mini App
    ↓
Backend
    ↓
Telegram Bot
    ↓
Закрытый Telegram Channel
```

После отправки фотографии бот получает информацию о сообщении.

В Firestore сохранять только метаданные:

```json
{
  "storage": "telegram",
  "telegram_chat_id": -100123456789,
  "telegram_message_id": 8421,
  "telegram_file_id": "AgAC...",
  "telegram_file_unique_id": "AQAD..."
}
```

Само изображение в Firestore или Firebase Storage не хранить.

---

# 9. OCR / Vision AI

Для анализа фотографий использовать Gemini API.

Это не классический OCR.

Задача AI — распознать конкретные позиции в электронном отчёте r_keeper.

Например:

```text
Дымный коктейль
Дымный коктейль 2
Чай
Вода
Кола
```

Где:

```text
Дымный коктейль = кальян
Дымный коктейль 2 = замена
```

AI должен определить только необходимые значения.

Например:

```json
{
  "hookahs": 5,
  "replacements": 4
}
```

Не нужно заставлять AI рассчитывать зарплату.

---

# 10. Pipeline обработки отчёта

После загрузки фотографии:

```text
1. Мастер фотографирует отчёт
2. Mini App отправляет фотографию backend
3. Backend сохраняет фотографию в Telegram Channel
4. Telegram возвращает message_id/file_id
5. Backend получает изображение
6. Backend отправляет изображение Gemini
7. Gemini возвращает структурированный JSON
8. Backend валидирует JSON
9. Backend сохраняет AI result в Firestore
10. Backend рассчитывает продажи
11. Backend рассчитывает зарплату
12. Смена закрывается
```

Временный файл, если он необходим для обработки Gemini, не должен постоянно храниться на сервере.

---

# 11. AI Response

Gemini должен возвращать строго структурированный JSON.

Например:

```json
{
  "hookahs": 5,
  "replacements": 4
}
```

Можно также хранить:

```json
{
  "hookahs": 5,
  "replacements": 4,
  "confidence": 0.97
}
```

Но `confidence` не должен быть единственным критерием доверия к результату.

Backend должен самостоятельно валидировать результат.

---

# 12. Проверка результата AI

Backend должен проверять:

```text
hookahs >= 0
replacements >= 0
```

Также должны быть предусмотрены проверки аномальных результатов.

Например, если за одну смену AI определил 150 продаж, система должна пометить результат как подозрительный и отправить его на ручную проверку.

Это не должно автоматически изменять зарплату без возможности администратора проверить данные.

---

# 16. Смена

Каждая смена обязательно привязана к:

```text
location_id
```

То есть смена должна содержать:

```json
{
  "location_id": "location_1"
}
```

Нельзя создавать смену без точки.

# 17. Открытие смены

После выбора точки мастер нажимает:

```text
Открыть смену
```

Система предлагает:

```text
Кто работает?

[ Соло ]

[ Выбрать второго мастера ]
```

Если соло:

```text
first_master_id = current_master
second_master_id = null
```

Если выбран второй:

```text
first_master_id = current_master
second_master_id = selected_master
```

Очень важно:

**Мастер, который открывает смену, всегда является первым мастером.**

Первый мастер получает:

```text
1.0 смены
```

Второй мастер:

```text
0.5 смены
```

# 18. Работа двух мастеров

Одна физическая смена должна существовать как одна запись.

Например:

```text

Точка: Точка 1

Первый мастер:
Данияр

Второй мастер:
Руслан
```

Эта смена отображается в истории обоих мастеров.

Для Данияра:

```text
1 смена
```

Для Руслана:

```text
0.5 смены
```

# 19. Распределение продаж

Основная формула:

```text
total_sales = hookahs + replacements
```

При двух мастерах:

```text
second_sales = total_sales // 2
first_sales = total_sales - second_sales
```

Остаток всегда получает первый мастер.

Пример:

```text
5 кальянов
4 замены

total_sales = 9
```

Распределение:

```text
first_sales = 5
second_sales = 4
```

---

# 20. Зарплата

У каждого сотрудника:

```text
salary_base
salary_per_sale
```

Например:

```text
salary_base = 3000
salary_per_sale = 1500
```

## Соло

```text
salary =
salary_base +
total_sales × salary_per_sale
```

Пример:

```text
3000 + 9 × 1500
= 16 500 ₸
```

---

# 21. Два мастера

Первый:

```text
salary =
3000 +
first_sales × 1500
```

Второй:

```text
salary =
1500 +
second_sales × 1500
```

Пример:

```text
9 продаж

Первый:
5 продаж
3000 + 5 × 1500
= 10 500 ₸

Второй:
4 продажи
1500 + 4 × 1500
= 7 500 ₸
```

# 30. Ревизия

Ревизия должна быть привязана к точке и периоду.

Например:

```text
Точка 1
Август 2026
```

В начале периода:

```text
Сколько должно быть
```

В конце:

```text
Сколько есть
```

Также:

```text
Общее количество смен
```

Формула:

```text
revision_difference =
(
  (how_many_should_be - how_many_are)
  / total_shifts
)
× employee_shifts
```

Количество смен мастера рассчитывается с коэффициентами:

```text
полная смена = 1
смена вторым мастером = 0.5
```

Пример:

```text
Всего смен:
30

Данияр:
20 полных
2 половинных

employee_shifts =
20 + (2 × 0.5)
= 21
```

Результат ревизии должен рассчитываться персонально для каждого мастера.

Ревизии также должны быть привязаны к конкретной точке.

# 33. Backend

Backend отвечает за всю критическую бизнес-логику.

Frontend никогда не должен самостоятельно решать:

* имеет ли пользователь доступ;
* какую точку он может выбрать;
* сколько продаж было;
* сколько заработал мастер;
* сколько смен у мастера;
* какой результат ревизии;
* может ли пользователь изменить данные.

Frontend только отправляет запрос.

Backend проверяет права и выполняет действие.

---

# 34. Firebase Security

Необходимо разработать корректные Firestore Security Rules.

Нельзя полагаться только на frontend.

Необходимо исключить возможность:

```text
master A
→ отправляет employee_id мастера B
→ получает зарплату мастера B
```

или:

```text
master
→ меняет salary
```

или:

```text
master
→ меняет final_hookahs
```

Все подобные операции должны быть запрещены.

# 38. Состояния смены

Предусмотреть состояния:

```text
OPEN
PROCESSING
CLOSED
CORRECTED
```

Например:

```text
OPEN
```

Мастер работает.

После загрузки:

```text
PROCESSING
```

AI анализирует фотографию.

После успешной обработки:

```text
CLOSED
```

Если администратор изменил данные:

```text
CORRECTED
```

При необходимости добавить отдельное состояние:

```text
ERROR
```

если AI не смог обработать отчёт.

```text
Кальяны
Замены
```

после чего backend рассчитает зарплату.

# 40. Главные бизнес-правила

salary_per_sale = 1500

# 41. Пример полного сценария

Данияр открывает Telegram.

Нажимает:

```text
/start
```

Backend проверяет его Telegram ID.

Данияр найден в Firestore.

Бот показывает:

```text

```

Данияр открывает Mini App.

Появляется:

```text
Выберите точку

[ Точка 2 ]
```

Данияр выбирает:

```text
Точка 1
```

Нажимает:

```text
Открыть смену
```

Выбирает:

```text
Руслан
```

Создаётся:

```text
Смена №154

Точка: Точка 1

Первый:
Данияр

Второй:
Руслан
```

После работы Данияр фотографирует r_keeper.

Фото отправляется в Telegram Storage.

Gemini распознаёт:

```json
{
  "hookahs": 5,
  "replacements": 4
}
```

Backend:

```text
total_sales = 9
```

```text
Данияр = 5
Руслан = 4
```

Зарплата:

```text
Данияр:
3000 + 5 × 1500
= 10 500 ₸

Руслан:
1500 + 4 × 1500
= 7 500 ₸
```

Смена закрыта.

Оба мастера видят её в своей истории.
